# Design: p3-restore-and-ship

## Context

P0–P2 (archived) established: tmux as the sole session source of truth (`garage/<workspace>/<label>` session names, `tmux ls` the list API); a `StatusStore` fed by a hybrid poller (`claude agents --json`, 2s interval) + Claude Code HTTP hooks, pushed to the UI over SSE; a workspace registry (`~/.garage/state.json`, currently `{workspaces, hookToken}`, directory-mapping only, atomic temp-file+rename writes); a multi-terminal grid with a single window-level `keydown` listener whose bindings are live only when `document.activeElement.closest(".xterm")` is null; and a diff/review pane with a `code` escape hatch. The daemon is deliberately near-stateless — tmux and git are re-queried live, `state.json` holds only what can't be recomputed.

Two gaps stand between this and a shippable tool. First, tmux's own server dies on reboot — every garage session vanishes, along with the illusion of persistence that's the whole pitch. What survives reboot is the Claude Code conversation itself: `claude` keeps its transcripts under `~/.claude`, keyed by a `sessionId`, independent of the tmux process tree — so `claude --resume <sessionId>` can bring a conversation back even though its terminal is gone. The poller already observes that `sessionId` on every tick, via the same `claude agents --json` join (`pid` → pane_pid → tmux session name) hooks.js's `resolveSessionIds` also relies on — it has just never been recorded anywhere. Second, running garage today means a checkout plus two dev servers (`vite`, the daemon) — fine for the author, a non-starter for `npx claude-garage` as IDEA.md's packaging goal and P3's binary gate ("fresh clone → `npx claude-garage` works on a second machine") require.

This design covers both: session-restore metadata and its endpoints, and the packaging entrypoint that serves the built UI from the same daemon process. It also closes P1's one explicitly-deferred open question (no keyboard-only terminal blur) and adds a `?` help overlay, since a shipped tool needs discoverable keybindings more than a personal dev tool does.

## Goals / Non-Goals

**Goals:**
- Define the resume-metadata schema added to `~/.garage/state.json`, its write/delete lifecycle, and how it survives the existing schema-defaulting pattern in `registry.js`'s `readState()`.
- Define how `GET /api/sessions` surfaces restorable (tmux-dead, metadata-alive) sessions alongside live ones, and the restore endpoint's single/bulk contract and failure mode.
- Resolve P1's open question: a keyboard-only chord to blur a focused terminal back to chrome-navigation mode, and the mechanism that reliably intercepts it ahead of xterm.js.
- Define the `?` help overlay: content scope, layering, and its fit into the existing suppression/overlay conventions P2 established.
- Define the `npx claude-garage` entrypoint: prerequisite checks, same-process UI+API serving, the Origin allowlist change it requires, and shutdown semantics that never touch tmux.
- Define best-effort browser auto-open with no new dependency.
- Define the README's structure (content itself is a tasks.md deliverable).

**Non-Goals:**
- Publishing to the npm registry (the user's own account/call).
- Linux desktop notification support (macOS-only, per P1's existing `D-notify` split).
- `garage deck` tmux-native layout (deliberately deferred since IDEA.md's surface decision).
- Any auto-update mechanism for the published package.
- Auto-restore on daemon start without user action (considered and rejected — see D-restore-flow).
- Any change to terminal-bridge, status-detection, or diff-review semantics beyond what restore/packaging require.

## Decisions

**D-resume-meta — `state.json` gains a `sessions` map, written opportunistically by the poller.**

Schema addition: `{"sessions": {"garage/<workspace>/<label>": {"claudeSessionId": "...", "workspace": "...", "label": "..."}}}`, alongside the existing `workspaces` and `hookToken` keys. `registry.js` gains `getSessionMeta`/`listSessionMetas`/`upsertSessionMeta`/`deleteSessionMeta`, following the exact read-modify-atomic-write pattern `upsertWorkspace` already uses. `readState()`'s existing shape-defaulting (`parsed.workspaces` invalid → `{}`) is extended to also default `parsed.sessions` to `{}` when missing or malformed — this is the migration story: an existing installation's `state.json` (pre-P3, no `sessions` key) loads exactly as it does today, and gains the key silently on the first write after upgrade. No explicit migration script needed.

Write path: `poller.js`'s `tick()` already computes, per garage session, the joined `claude agents --json` entry (`agentByPid`/`cwd` fallback) — that entry carries `sessionId` (P1's `D-status` documents the shape as `{pid, cwd, sessionId, status}`). When a garage session id resolves to an agent, compare that agent's `sessionId` to what's currently recorded for the id (via `getSessionMeta`); write only on a genuine change (first observation, or a different value than last time) via `upsertSessionMeta(id, {claudeSessionId, workspace, label})`. This bounds write frequency: a `claude` process's `sessionId` is stable for the life of one conversation, so after the first tick following spawn this becomes a no-op comparison on every subsequent 2s poll — the file is touched once per session's lifetime in the common case, not every tick. This mirrors the write discipline `getHookToken()` already applies (generate-and-persist once, read thereafter) and avoids reintroducing the write-amplification P1's `D-registry` was careful to avoid.

Delete path: `DELETE /api/sessions/:id` in `sessions.js`, after `killSession()` succeeds, calls the new `deleteSessionMeta(id)`. This is the "deliberate kill" signal — pressing the kill control means the user is done with that conversation, so there's nothing to offer restoring later.

Kept-on-vanish: when `poller.js`'s `tick()` detects a session id disappeared from `tmux ls` (the existing `dropSession(id)` branch, today only used for `StatusStore` cleanup), the `sessions` meta entry is deliberately left untouched. That branch fires for exactly the reboot/crash case — the whole tmux server died out from under every session at once, none of them went through the API's `DELETE`, so all their resume metadata survives to be offered as restorable on the next `GET /api/sessions`.

Staleness is expected and bounded: `claudeSessionId` references a conversation transcript stored under `~/.claude`, which is why it survives a reboot at all — but it can go stale if the user prunes that conversation through `claude`'s own history tooling, independent of garage. That failure surfaces at the `claude --resume` step itself (see D-restore-flow and Risks) rather than being pre-validated here — validating "does this sessionId still resolve" would mean shelling out to `claude` speculatively for every restorable entry on every `GET /api/sessions`, which is exactly the kind of poll-tick cost D-resume-meta's write discipline exists to avoid.

Alternatives considered: writing the mapping on every poll tick unconditionally — rejected as needless `state.json` churn for a value that essentially never changes tick-to-tick. A separate metadata file — rejected for the same reason P1's `D-registry` gave against a second session store: one small file, one atomic writer, one schema. Resolving `claudeSessionId` lazily at restore time by scanning `~/.claude`'s conversation directory for a cwd match — rejected because once the tmux session (and its pid) is gone, there is no reliable way to associate a dead session with a specific conversation after the fact; the mapping has to be captured while the process is alive, at exactly the observation point the poller already has.

**D-restore-flow — merged listing, explicit single/bulk restore endpoint, no auto-restore.**

`GET /api/sessions` continues to return live sessions from `listSessions()` + `getStatus()` unchanged, then appends one entry per `sessions` meta record whose id has no matching live tmux session: `{id, workspace, label, dir: <from getWorkspace(workspace)>, status: "restorable", restorable: true}`. Composing the entry from the registry's live workspace lookup (not a cached dir inside the meta record itself) means a workspace re-registered to a new path since the crash is reflected correctly. Reusing the existing session shape (rather than a parallel `restorableSessions` array) means the UI's existing `buildGroups`/rail code needs only to branch on the `status`/`restorable` field, not maintain a second list end-to-end. `"restorable"` is a fifth value alongside the four `StatusStore` states — distinct on purpose, since a restorable entry isn't really "idle," it's "not running at all yet" — rendered as a dimmed row with a distinct glyph (`⟳`) per the proposal.

`POST /api/sessions/restore` accepts `{id}` for a single restore or `{all: true}` for every currently-restorable entry. For each target: look up its meta record, re-resolve the workspace's directory via `getWorkspace(workspace)` (never the meta's own copy, for the same freshness reason as the listing), confirm the directory still exists on disk (mirroring the existing `stat` check `sessions.js`'s spawn path already performs) and that a live tmux session with that id doesn't already exist. Any of those failing returns 409 with a reason string (`"workspace no longer registered"` / `"registered dir no longer exists"` / `"session already running"`) for that id, and — critically — the meta entry is left in place rather than deleted, since these are all conditions the user might fix (re-register the workspace, restore the directory) and retry, unlike a deliberate kill. On success: `tmux new-session -d -s <id> -c <dir> claude --resume <claudeSessionId>`, extending `tmux.js`'s existing `createSession()` (or a parallel `createResumedSession()`) with the extra `--resume` argument. `{all: true}` runs this per-entry and returns a per-id result list so a partial failure (one stale workspace among five) doesn't block the rest.

Alternative considered and rejected: auto-restoring every restorable session the moment the daemon starts. Rejected for three reasons: it's surprising — launching `npx claude-garage` (or restarting the daemon) shouldn't silently spawn N live `claude` processes, each consuming API usage, without the user asking; IDEA.md's own wording is "offers restore," not "restores automatically," and every other session lifecycle action in this system (spawn, kill) is already explicitly user-initiated, so auto-restore would be the one inconsistent exception; and if a workspace directory moved or vanished since the crash, a silent background restore fails with no user primed to notice, whereas a visible "Restore" control in the rail sets that expectation up front.

**D-blur-chord — `Ctrl+\`` blurs the focused terminal, intercepted per-terminal via `attachCustomKeyEventHandler`.**

`Ctrl+\`` (Control+backtick) is the new keyboard-only path back to chrome-navigation mode, closing the gap P1's `D-keys` explicitly left open (blur was mouse-click-only: header/rail/gutter `onMouseDown` calling `blurActiveTerminal()`). Alternatives considered: double-tap `Esc` — rejected because `Escape` already carries real meaning inside a live terminal (Claude Code's own TUI uses it to interrupt generation; tmux copy-mode uses it too), and overloading a double-tap on a key with existing single-tap terminal semantics is exactly the ambiguity P1's `D-keys` avoided by rejecting modifier chords that collide with terminal-native bindings — reintroducing it here for the one binding whose entire job is "work even while a terminal has focus" would be self-defeating. `Ctrl+[` — rejected outright, not just as inferior: in every terminal, including xterm.js, `Ctrl+[` **is** the `Escape` control byte (0x1B); binding it to blur would silently break real `Escape` delivery to the pty, the opposite of the intended effect. `Ctrl+\`` survives because it's unclaimed by tmux's default prefix, readline, or Claude Code's own bindings.

Mechanism: this cannot be handled by App.jsx's existing single `window.addEventListener("keydown", ...)`. That listener is exactly right for bindings that fire only when *no* terminal has focus (P1/P2's suppression rule checks `document.activeElement.closest(".xterm")` and bails), but this binding's entire purpose is to fire *while* a terminal has focus, and xterm.js attaches its own keydown handling directly to its internal DOM node, which processes (and can forward to the pty) a keystroke before it's useful to reason about at the window level for this case. The reliable mechanism is `Terminal.attachCustomKeyEventHandler(handler)` — registered per xterm.js instance, wherever terminals are constructed (`TerminalGrid`/`SessionTerminal`) — returning `false` when the handler recognizes `Ctrl+\`` to suppress xterm's own default processing of that keystroke, and instead invoking the same `blurActiveTerminal()` App.jsx already exposes and threads down as `onBlurChrome`. This is a per-terminal registration, not a second window-level listener, because the whole point is intercepting the key while that specific terminal owns DOM focus.

**D-help — `?` opens a static keybinding overlay, above review mode, suppressed the same way as every other chrome binding.**

`?` opens a full-screen static overlay (same `position: fixed; inset: 0` pattern P2's `ReviewMode` established) listing every keybinding across P0–P3 (`1`–`9`, `[`/`]`, `a`, `Tab`, `j`/`k`, `r`/`Esc`, `v`, `o`, and the new `Ctrl+\`` and `?` itself). It renders at a higher z-index than `ReviewMode`'s own overlay so it's reachable even while review mode is open (a user checking "what does `v` do again" mid-review shouldn't have to exit review mode first). `?` is suppressed while a terminal is focused, under the identical `document.activeElement.closest(".xterm")` rule every other chrome binding already obeys in App.jsx's keydown handler — no special case. `Esc` closes it, extending App.jsx's existing `Escape` branch (currently gated on `reviewMode`) to also check help-overlay-open state; if both are open, `Esc` closes the topmost (help) first, consistent with the z-order. No serious alternative to the key itself was considered: `?` (Shift+/) is the near-universal "show shortcuts" convention (Slack, Linear, Gmail, Superhuman) and nothing in P0–P2 claims it.

**D-packaging — `bin/garage.js` prerequisite-checks, then starts the daemon with same-process static UI serving.**

`bin/garage.js`: ESM, `#!/usr/bin/env node`. First runs `execFile` version checks for `tmux` and `claude` on `PATH`; either missing (`ENOENT`) produces a readable, actionable error — naming which binary is missing and an install hint (e.g. `tmux` via Homebrew, `claude` via the Claude Code CLI installer) — and exits 1 before anything else runs, rather than letting the daemon fail deeper and more cryptically the first time it shells out to a missing binary. Once both checks pass, the bin imports the daemon's app-construction logic (likely `index.js` refactored to export a `createApp()`/`start()` rather than only running at module load, so the bin can call it in-process instead of spawning a second `node`) with `GARAGE_SERVE_UI=1` set.

Daemon change, flag-gated: when `GARAGE_SERVE_UI` is set, register `@fastify/static` to serve `ui/dist` at `/`, alongside the existing `/api/*` and `/term/*` routes, in the same Fastify instance, same port. When unset (today's `npm run dev` workflow, where Vite's dev server on :5173 already serves the UI via its own proxy to the daemon), static registration is skipped entirely — gated on the flag, not on route order, so dev mode never double-registers a static root and the two workflows can never collide. `@fastify/static` is the first new daemon dependency; justified over hand-rolling static file serving (correct MIME types, conditional/cache headers, directory-traversal safety) which Fastify's own team already solved.

Origin allowlist (`security.js`'s `DEFAULT_ORIGINS`): gains `http://127.0.0.1:4747` and `http://localhost:4747`. Necessary because once the UI is served from the same origin as the API (in packaged mode), its own `fetch`/`EventSource` calls carry that Origin header, and `rejectForeignOrigins` would otherwise reject the UI's own state-changing requests — precisely the scenario this packaging mode exists to serve.

`package.json`: `bin: {"claude-garage": "bin/garage.js"}`; `prepack` runs `npm run build -w ui` so a fresh `ui/dist` always exists when the package is packed, without a manual pre-publish step; `files` field ships `daemon/src`, `ui/dist`, `bin` only — no devDependencies, UI source, or test artifacts.

Shutdown: `SIGINT`/`SIGTERM` handlers call Fastify's `app.close()` (which already runs the existing `onClose` hook stopping the poller) and then exit — and explicitly never call `killSession` or otherwise touch tmux. This needs stating plainly because it's an easy, wrong "cleanup" instinct to reach for; tmux sessions are an independent process tree from the daemon, and the entire product promise (IDEA.md: "close the app, nothing dies") depends on shutdown never crossing that boundary.

Alternative considered for UI serving: a separate static file server process alongside the daemon (e.g. the `serve` package on its own port). Rejected — two processes means either two ports (browser has to know both, and the "one npx command, one URL" pitch breaks) or a reverse proxy to unify them, which re-introduces the exact CORS/Origin-allowlist coordination this design closes by putting both concerns in one Fastify instance. One process, one port is strictly simpler and consistent with the "daemon is almost stateless, thin" philosophy P0–P2 already established.

**D-open-browser — best-effort `open` on darwin, no dependency.**

`bin/garage.js` always prints the URL (`http://127.0.0.1:<port>/`) to stdout, so a headless run, a CI check, or a user who ignores auto-open still has it. Additionally, when `process.platform === "darwin"`, it best-effort spawns `open <url>` via `execFile`, swallowing any failure silently (the same "never throw for a non-critical convenience" discipline `notify.js`'s `osascript` call already follows). No new npm dependency (an `open`-style package was considered and rejected) — `open` is a stock macOS binary, the same reasoning already used for `osascript` (D-notify, P1) and for choosing `@fastify/static` over inventing something: don't add a dependency for something the OS or the framework already ships.

**D-readme — structure now, content in tasks.**

Fixed section order: title + one-line SEO description (IDEA.md's SEO rule: "Claude Code session manager", "parallel sessions", "grouped terminals", "diff review" all present in the H1/description, never carried by the brand name alone); install (`npx claude-garage`); prerequisites (tmux, Claude Code CLI, macOS) stated in the same terms as `bin/garage.js`'s own prereq-check error messages, so the two never drift apart; hooks setup pointing at `GET /api/hooks/snippet` (matching the existing `HooksBanner` discovery flow rather than duplicating the JSON payload inline in prose); a single keybindings table covering all of P0–P3's bindings including the new `Ctrl+\`` and `?`; an escape-hatch section stating the philosophy IDEA.md already fixes explicitly (`tmux attach` from any terminal; `o`/open-editor-root from the UI; garage owns orchestration + triage, VS Code/iTerm stay the deep tool); a development section for contributors (`npm install`, `npm run dev`, workspace layout). Content itself is written as part of the tasks for this change, not fixed here.

## Risks / Trade-offs

- [Stale `claudeSessionId`: the referenced conversation was pruned or is otherwise unresolvable by `claude --resume`] → the failure surfaces visibly inside the newly-spawned terminal itself (claude's own error output) rather than being silently swallowed; acceptable and documented (README + help overlay note that restore can fail this way) rather than pre-validated, since pre-validating would mean shelling out speculatively on every listing.
- [`state.json` schema growth: existing installations' files predate the `sessions` key] → `readState()`'s existing shape-defaulting is extended to default a missing/malformed `sessions` to `{}`, matching the exact pattern already used for `workspaces`; no explicit migration step required.
- [`@fastify/static` version compatibility with Fastify v5] → pin to a version verified against the daemon's existing `fastify: "^5.3.0"` during implementation; this is the first new daemon dependency since P0, so compatibility is checked explicitly rather than assumed.
- [Port conflict: `EADDRINUSE` on 4747] → `index.js`'s existing `app.listen(...).catch(...)` is extended to special-case `EADDRINUSE` with a readable message suggesting the `GARAGE_PORT` environment variable as the fix, rather than the current generic error dump.
- ["Restore all" spawns many `claude` processes concurrently] → user-initiated and visible (the control is explicit in the rail), not automatic; no daemon-side throttling is added in this design (see Open Questions).
- [Write-amplification regression if `claudeSessionId` churns unexpectedly, e.g. a user manually starting a fresh conversation inside an existing garage tmux session] → bounded by D-resume-meta's change-only write guard; worst case is one extra write per actual change, not per poll tick.

## Open Questions

- Whether `POST /api/sessions/restore {all: true}` needs a concurrency cap or stagger to avoid a burst of simultaneous `claude` process starts hitting API rate limits, or whether sequential-enough-in-practice (tmux spawn is fast, not truly parallel) makes this moot — revisit from real usage rather than pre-optimizing.
- Exact `@fastify/static` version pin, once compatibility with Fastify `^5.3.0` is verified during implementation.
- Whether the help overlay and review mode ever need independent z-index/focus handling beyond "help renders on top," or whether that's sufficient — no evidence of a problem yet.
- Whether `bin/garage.js`'s prerequisite checks should enforce minimum versions (e.g. tmux ≥ 3.2, per P0's original constraint) or only presence — ship presence-only first, tighten if a version-specific bug report ever surfaces.
